# Цифровой сомелье: подбор «блюдо → сорт → бутылка»

Реализация ТЗ «Доработка цифрового сомелье» (18.10.2026). Работает рядом с диалоговым сомелье (`/api/sommelier/ask`,
[`SOMMELIER.md`](SOMMELIER.md)) и не меняет его. Код — `app/sommelier/pairing/`, данные — `app/sommelier/data/`,
тесты — `tests/test_sommelier_pairing.py`.

**Главное правило: рекомендуются только российские вина из каталога сервиса.** Покупатель остаётся в нашем торговом
пространстве: зарубежных бутылок нет ни в одном сценарии. Если покупатель называет зарубежное вино, сервис ищет ему
российский аналог в каталоге (раздел 4).

```
запрос ──► разбор (правила / LLM, JSON-схема) ──► профиль блюда (справочник 71 блюдо │ оценка LLM │ ключевые слова)
                                                        │
справочник сортов (vine_tastes.csv + grapes.json) ──► оценка каждого сорта 0–100 (веса pairing_config.json)
                                                        │  сорта ≥ 60, не больше 5
CatalogProvider (каталог сканера │ demo │ retail) ──► только российские бутылки ──► оценка бутылки ± стиль ──► 3 бутылки
                                                        │
                       объяснение: шаблон │ LLM + проверка названий, цен, стоп-листа (иначе шаблон)

«аналог Шабли» ──► свойства зарубежного вина (LLM │ справочник стилей) ──► ближайшие российские бутылки ──► 3 аналога
```

## 1. Справочник сортов (ТЗ п. 2)

| Файл | Что в нём |
|---|---|
| `data/vine_tastes.csv` | исходная таблица без изменений (9 сортов) |
| `data/grapes.json` | `grape_id`, `aliases`, `sweetness_default`, `oak_variants`, `is_russian_origin`, `pairing_rules`, `story`, `status`, `signed_by`; блок `russian_extension` — 7 российских сортов/стилей; `geo` — закрытые списки стран и регионов |

Парсер (`reference.parse_grapes_csv`) читает CSV как есть (UTF-8 с BOM, «/» в составных значениях) и переводит в числа:

| Поле | Значения | Число |
|---|---|---|
| Танины | Нет (0) / Низкие / Низкие-Средние / Средние / Средние-Высокие / Высокие | 0 / 1 / 1,5 / 2 / 2,5 / 3 |
| Кислотность | Низкая / Низкая-Средняя / Средняя / Высокая / Очень высокая | 1 / 1,5 / 2 / 3 / 4 |
| Тело | Лёгкое / Лёгкое-Среднее / Среднее / Среднее-Полное / Полное | 1 / 1,5 / 2 / 2,5 / 3 |

Неизвестное значение — `ReferenceDataError` с файлом, номером строки и полем.

`pairing_rules` — правило из таблицы, разложенное на блюда: `{"term": "жареное мясо", "tags": ["fried_meat", "grilled_meat"], "weight": 1.0}`.
Теги связывают правило с блюдами справочника. У Шардоне правила с условием `"when": {"oak": "да"|"нет"}`, плюс `oak_profile`
(тело с дубом — полное, без дуба — среднее). Сорт с `oak_variants = оба` оценивается в обоих стилях, берётся лучший.
Кухня в правиле («блюда кавказской кухни», «азиатская кухня») — поле `cuisines`.

Российское расширение: Цимлянский чёрный, Сибирьковый, Кокур белый, Пухляковский, Голубок, Рислинг и Алиготе
российских регионов (как стили). **Профили заполнены командой как черновик** (`status: draft`, `signed_by: null`), поэтому
в выдаче не участвуют. После подписи сомелье-эксперт меняет `status` на `active` и заполняет `signed_by`, затем повышает `version`.

## 2. Справочник блюд (ТЗ п. 4.1)

`data/dishes.json`: 71 блюдо, оси 0–3 — `body`, `fat_protein`, `acid`, `spicy`, `salty`, `sweet`, плюс `cuisine`, `synonyms`
(«шашлык», «шашлычок», «мясо на мангале») и `tags` для правил сортов. `fat_protein` понимается как в ТЗ — «жир и белок,
требует танинов»: у рыбы, сливочных соусов и десертов он низкий, у стейка и зрелого сыра — высокий.

Поиск блюда: самый длинный синоним целиком → основа слова («к утке», «под устриц») → нечёткое сравнение.
Блюда нет в справочнике → профиль строит LLM (`source: llm`, `estimated: true`); без LLM — грубая оценка по ключевым словам
существующего разбора `dishes.parse_dish` (`source: keywords`); если и это не удалось — уточняющий вопрос.

## 3. Оценка сорта и ранжирование (ТЗ п. 4.2–4.3)

Оценка = `base` (80) − штрафы + бонусы, обрезается до 0–100. Веса — `data/pairing_config.json`:

| Правило | Вес |
|---|---|
| Тело вина ≈ насыщенность блюда | −12 за единицу расхождения |
| Танины ≈ жир и белок блюда | −12 за единицу расхождения |
| Кислотность вина ≥ кислотности блюда | −8 за единицу недостачи |
| Острое блюдо и танины | −6 × острота × танины / 3 |
| Острое или солёное: кислотность и сладость вина | бонус до +10 |
| Сладкое блюдо (sweet ≥ 2), вино суше блюда | −40 |
| Сладкое вино к несладкому блюду (добавлено при настройке) | −10 за ступень сверх одной |
| Блюдо названо в правиле сорта | +25 × вес пункта правила |
| Кухня совпадает с правилом | +10 |

Ранжирование бутылок: сорта с оценкой ≥ 60, не больше 5 → **только российские** бутылки каталога по фильтрам (цвет, сладость,
бюджет, магазин) → оценка бутылки = оценка сорта в стиле бутылки − 5 за каждую ступень сладости от правила сорта →
бутылки ниже 60 отбрасываются. Стиль бутылки (`scoring.bottle_profile`) уточняет профиль сорта: дуб; розовое из красного сорта —
почти без танинов и легче; белое из красного (blanc de noirs) — без танинов; игристое — свежее и легче; признаки из описания
карточки (тело, танины, кислотность) — с весом 0,5. Так сотни Каберне каталога различаются между собой.

Выдача — 3 российские бутылки без повторов: лучшее сочетание → лучшая бутылка другого сорта → вариант в другой цене
(если цены есть, разница ≥ 30 %), иначе ещё один сорт или винодельня. Одна винодельня — не больше одного раза.
Если в каталоге нет цен (каталог сканера), бюджет не применяется, а в ответе пометка `notes: ["В каталоге нет цен — бюджет не учтён."]`.

Каждая оценка раскладывается на факторы `{rule, points, text}` — их показывает кнопка «Почему это сочетание?».

**`similar(grape)`** (п. 4.4): евклидово расстояние по танинам, кислотности, телу и цвету (вес цвета 3, аналог не дальше 1,5),
фраза-«мост»:
«Любите Каберне Совиньон? Попробуйте Красностоп Золотовский: та же плотность и танины, больше пряности.»
Бутылки — российские: сначала автохтон-аналог, затем тот же сорт российского производства.
**Обратный сценарий** (п. 4.5): по slug — 5 блюд справочника с наивысшей оценкой и правило сорта.

### Метрики на эталоне (п. 8.1)

`data/pairing_reference.json` — 70 блюд, у каждого 1–3 подходящих и 1–2 неподходящих сорта (**черновик команды,
`status: draft`**, до пилота подписывается экспертом). Проверка — `python scripts/eval_pairing.py` и тест `test_reference_metrics`:

| Метрика | Цель | Сейчас |
|---|---|---|
| Top-3 hit rate | ≥ 85 % | 97,1 % (промахи: шоколадный десерт, голубые сыры) |
| Неподходящие сорта в тройке | ≤ 5 % | 0 % |
| Есть российская бутылка, когда есть подходящий сорт (каталог сканера) | ≥ 90 % | 100 % |

## 4. Российский аналог зарубежного вина

Запрос «аналог Шабли», «замена Бароло», «что-то вроде новозеландского Совиньон Блан» (или `scenario: analog`,
`POST /api/sommelier/analog`):

1. **Свойства зарубежного вина.** С LLM — модель описывает вино по схеме `ForeignWine` (цвет, сладость, танины 0–3,
   кислотность 1–4, тело 1–3, сорта, дуб); ответ проверяется pydantic-схемой, при ошибке — повтор. Без LLM или при ошибке —
   справочник известных вин и регионов `data/foreign_styles.json` (Бордо, Бургундия, Шабли, Сансер, Мозель, Бароло, Риоха…)
   или сорт, названный в запросе. Ничего не найдено — уточняющий вопрос.
2. **Выбор аналога — алгоритм, не модель.** Кандидаты — российские тихие вина каталога того же цвета с активным сортом.
   Оценка (`scoring.score_analog`, веса `analog` в `pairing_config.json`): 100 − 15 × расстояние профилей (танины, кислотность,
   тело с поправками стиля бутылки) − 10 за ступень сладости + 10 за тот же сорт + 5 за дуб, если исходное вино в дубе; порог 55.
3. **Выдача** — до 3 бутылок разных сортов и виноделен с фразой «Похоже на «Шабли»: та же плотность и танины, свежее».

Ответ: `kind: analog`, `foreign` (свойства и их источник `llm`/`rules`), `wines`, `explanation`.

## 5. Каталог SKU (ТЗ п. 3)

`CatalogProvider`: `list_wines(filters)`, `get_by_slug(slug)`, `get_stock(slug, store_id)`, `health()`. Подбор работает только
с этим интерфейсом. Переключение — `CATALOG_SOURCE=service|demo|retail` в `.env`, без изменения кода. Фильтр «только российские»
ставит сервис подбора, поэтому он действует для любого источника.

- **ServiceCatalogProvider** (по умолчанию) — каталог сканера: российские вина базы распознавания (`wines_integrated.csv`,
  2108 вин; с сортом справочника — 1600). Сорт сопоставляется по aliases, сладость, дуб, игристость и признаки вкуса — из разбора
  описаний. Цен и остатков нет. Slug совпадает со slug распознавания этикеток.
- **DemoCatalogProvider** — `data/catalog_demo.csv`: 21 вымышленная бутылка, 12 российских, все производители «Демо-…»,
  `source = demo`, штрихкоды — корректные EAN-13 вымышленных товаров, остаток всегда «есть». Нужен для проверки интерфейса ритейла;
  9 зарубежных бутылок в выдачу не попадают.
- **RetailCatalogProvider** — методы объявлены и выбрасывают `NotImplementedError("Источник ритейлера не подключён")`;
  API отвечает 503 с этим текстом. Конфигурация: `RETAIL_SOURCE_KIND` (csv | api), `RETAIL_SOURCE_URL`, `RETAIL_API_KEY`,
  `RETAIL_REFRESH_CRON`.
- **Шаблон выгрузки** — `data/catalog_template.csv` (заголовок + строка-пример). Обязательные поля: `slug, name, producer, grape,
  color, sweetness, country, region, price_rub, retailer_sku, barcode`; необязательные: `oak` (по умолчанию — `oak_variants` сорта),
  `volume_l`, `store_id`, `stock_qty`, `is_russian` (по умолчанию вычисляется из `country`). Сорт — из справочника или его aliases,
  страна и регион — из закрытых списков `geo`, штрихкод — EAN-13. Проверка строк — `catalog.parse_catalog_row`.
- **Обогащение** (п. 3.4) — `pairing/enrich.py`: сорт, сладость и дуб из названия и описания (правила → LLM, сорт принимается
  только из aliases), любое выведенное поле ставит `needs_review`. Такие позиции в выдачу не попадают, пока их не проверит человек.
  Позиция без сорта не участвует в подборе по блюду, но доступна по slug.

## 6. LLM-слой (ТЗ п. 5)

LLM не выбирает вино: она разбирает запрос, описывает свойства зарубежного вина и формулирует объяснение. Интерфейс — `LLMClient.complete(system, user, max_tokens, json_mode)`, провайдер —
`SOMMELIER_LLM_PROVIDER=gemini|none` (ключ `GOOGLE_API_KEY`, модель `SOMMELIER_LLM_MODEL`). Без ключа или с `none` —
шаблонный режим: блюдо ищется по справочнику, текст строится по шаблону.

- **Разбор запроса**: модель возвращает JSON по схеме `LLMQuery` (`dish`, `dish_profile`, `budget_max`, `sweetness`, `color`,
  `liked_grape`, `occasion`). Ответ проверяется pydantic-схемой; при ошибке — повторный запрос с текстом ошибки, затем
  правила; если и правила ничего не нашли — уточняющий вопрос (`kind: clarify`).
- **Объяснение**: в промпт уходят только выбранные бутылки, их сорта, `pairing_text` и `story` российских.
- **Проверка ответа** (`check_explanation`): все переданные названия должны быть в тексте дословно; каждая цена должна совпадать
  с переданной; названия в «кавычках» и названия других бутылок каталога запрещены; стоп-лист 38-ФЗ («купите», «скидка», «акция»,
  «лучшее вино», советы о количестве); не длиннее 600 знаков. Любое нарушение — ответ заменяется шаблоном (`source.explanation: template`).
  Тест `test_zero_invented_bottles_on_200_queries` гоняет 200 запросов с моделью, которая выдумывает бутылку в каждом втором ответе.
- **Журнал**: все промпты и ответы — `media/sommelier/pairing_llm_log.jsonl` (без идентификаторов пользователя).

## 7. API (ТЗ п. 6.2)

В проекте версионируются только search-пайплайны (AGENTS.md), поэтому методы ТЗ `/v1/...` живут под `/api/sommelier/...`.
Версии справочников и весов приходят в каждом ответе в поле `versions`.

| ТЗ | Метод | Сценарий |
|---|---|---|
| `POST /v1/pairing/dish` | `POST /api/sommelier/pairing/dish` | С1, С4 (`dish_id`, `scenario: recipe`), С5 (`scenario: gift`), аналог (`scenario: analog` или текст «аналог …») |
| `GET /v1/pairing/wine/{slug}` | `GET /api/sommelier/pairing/wine/{slug}` | С2 |
| `GET /v1/similar/{grape_id}?russian=true` | `GET /api/sommelier/similar/{grape_id}?russian=true` | С3 |
| — | `POST /api/sommelier/analog` | российский аналог зарубежного вина |
| `GET /v1/grapes`, `GET /v1/dishes` | `GET /api/sommelier/grapes`, `GET /api/sommelier/dishes` | справочники |
| `GET /v1/health` | `GET /api/sommelier/health` | состояние, источник каталога |

```bash
curl -fsS -X POST http://127.0.0.1:8080/api/sommelier/pairing/dish -H 'Content-Type: application/json' \
  -d '{"query": "что взять к шашлыку, до 1500, не сладкое", "filters": {"color": "Красное"}}'
```

Ответ (сокращённо):

```json

                   "cuisine": "кавказская", "source": "dictionary", "estimated": false},
  "grapes": [{"grape_id": "saperavi", "name": "Саперави", "score": 100, "factors": [...], "passed": true}, ...],
  "wines": [{"slug": "...", "name": "AGORA Саперави", "producer": "AGORA WINERY", "region": "Кубань", "country": "Россия",

             "role_label": "Лучшее сочетание", "explanation": "Саперави: ...", "story": "...", "url": "https://...",
             "why": {"rule": "Мощная структура требует насыщенных вкусов. ...", "factors": [...], "adjustments": [...]}}, ...],
  "explanation": "К блюду «Шашлык»: ...",

```

`kind`: `pairing`, `gift`, `analog`, `similar` (запрос «люблю Каберне» без блюда), `clarify` (поле `question`), `guardrail`
(несовершеннолетний, за рулём и т. п. — общие правила сомелье). При `catalog_source = demo` клиент показывает плашку «Демо-данные».

**Связь с распознаванием этикеток.** Каталог сканера и база распознавания — одни и те же вина с одними slug, поэтому
распознанная этикетка (`/api/cascade/search`) сразу получает через `GET /api/sommelier/pairing/wine/{slug}` 5 блюд, правило
сорта и «мост» к российскому автохтону. При `CATALOG_SOURCE=demo|retail` slug, которого нет в каталоге, ищется в базе распознавания.

## 8. Интерфейс сканера

- **«Вино к блюду»** на главном экране: строка запроса, выбор сценария (к блюду / подарок / аналог зарубежного вина), фильтры
  (цвет, сладость, бюджет), три карточки российских бутылок со ссылкой на карточку вина; для аналога — свойства зарубежного вина.
- **«Подойдёт к блюдам»** в карточке распознанного вина: 5 блюд, «Почему это сочетание?» с правилом сорта, история сорта и блок
  «Похожее, но российское» с фразой-«мостом» и российскими бутылками.
- Карточка бутылки: название, производитель, регион, цена, отметка «Россия», роль, 1–2 строки объяснения, «Почему это сочетание?»
  с правилом сорта и вкладом каждого правила скоринга. Плашка «Демо-данные» — при `catalog_source = demo`.
- **18+**: при первом входе в любую функцию сомелье (подбор, чат, оценка сочетания) — вопрос о возрасте, ответ хранится на устройстве.
